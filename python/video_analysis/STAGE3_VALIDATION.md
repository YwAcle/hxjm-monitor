## 实际借鉴和实现

阅读了 ActiveVAU 的 frame_capture、stream_manager、time_alignment、useEventStream
和 VideoWithOverlay 的执行逻辑，并核对独立 demo 与正式 lanhu/Python。
借鉴懒启动复用、延迟空闲回收、有限检测历史、媒体进度到到达时间的映射，以及
有限 Canvas 播放缓存。ActiveVAU 的 RTSP PTS 最小到达时间锚点和 WebRTC
`receivedAt - serverLatency` 都是估计；HLS PROGRAM-DATE-TIME 不适用于当前 WHEP。
没有照搬它的跨协议提前量、无目标身份的插值或把旧框短暂显示当作精确同步。

- 后端：有新鲜解码帧才保留一次执行机会；需要时才启动共享模型，优先复用空闲
  已就绪模型。加载之后重取最新帧，源消失时不提交旧作业。默认空闲 60 秒回收。
  全局最多四个在途 camera/task 作业；浏览器数量不改变模型池规模。
- 状态：RTSP 连接、等待首帧、重连属于 capture；模型加载、任务等待、检测和
  推理错误属于 analyzer。每路独立。网页也根据真实视频帧进度显示等待新画面。
  结果本地过期持续显示“暂无新结果”，不会被心跳重新显示为模型加载。
- 时间：提供 PTS/解码时间来源，最低 RTT 服务器/浏览器时钟估计，以及最多 64 个
  有效结果。实时模式继续显示最新有效检测；同步模式按实际绘制帧的估计时间
  从历史选择结果（550 ms 容差，超过显示帧 80 ms 的未来结果不匹配）。
- 同步视频：默认目标额外延迟 650 ms，上限 1000 ms；底层 WebRTC 不暂停等待 AI。
  每路最多 32 帧/32 MiB；最多 12 fps、640×360 的本地副本。缺少 rVFC/媒体时间
  或缓存不能供帧时降级到实时。同步模式的显示分辨率因此可能低于原视频。
- 清理：乱序、过期、旧会话/旧 epoch、Worker 重启、源切换、后台恢复和零目标
  已覆盖。消费、淘汰、迟到异步结果和模式切换都释放 ImageBitmap。
