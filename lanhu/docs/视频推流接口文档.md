# 视频推流与前端展示接口文档

**适用工作目录**

- 推流处理服务：`/data/nfs_storage/hxjm/mtx`
- 前端工程：`/data/nfs_storage/hxjm/lanhu`
- 文档依据：当前 `mtx/config.yaml`、`mtx/docker/docker-compose.yml`、`mtx/control/ControlServer.cpp` 和 `lanhu/src/components/CenterPanel/components/MonitorGrid/WebRTCPlayer/index.jsx` 的实际实现。

## 1. 总体架构

浏览器不能直接播放 RTSP。当前链路如下：

```text
摄像头/设备 RTSP
        │ inputUrl
        ▼
ai-stream（FFmpeg 拉流、解码、AI处理、H.264编码）
        │ RTSP publish
        ▼
MediaMTX（RTSP接入与WebRTC转换）
        │ WHEP POST + SDP
        ▼
lanhu 前端 WebRTCPlayer（<video> 展示）
```

每路摄像头可以有一个或多个算法输出流：

| 流 | MediaMTX 路径示例 | 用途 |
|---|---|---|
| 原始流 | `live/camera_1` | 无算法框的原始画面 |
| 算法流 | `live/camera_1_deepsort` | AI处理后带框画面 |

当前前端优先播放算法流，算法流不可用或超过 3 秒没有新帧时切换原始流；算法流恢复后每 5 秒探活并切回算法流。

## 2. 服务地址和端口

Docker 部署时的默认端口：

| 服务 | 地址 | 说明 |
|---|---|---|
| MediaMTX RTSP | `rtsp://<host>:8554` | ai-stream 发布和读取 |
| MediaMTX WebRTC/WHEP | `http://<host>:8889` | 浏览器取流 |
| MediaMTX HLS | `http://<host>:8888` | 可选的 HLS 调试/兼容播放 |
| ai-stream 控制接口 | `http://<host>:19090` | 启停摄像头算法任务；生产环境应限制内网访问 |
| MediaMTX Control API | `http://127.0.0.1:9997` | 服务管理，不是浏览器播放接口 |

`mediamtx/mediamtx.yml` 已开启 `rtsp: yes`、`webrtc: yes`，WebRTC 地址为 `:8889`；Docker 还映射了 WebRTC ICE UDP `8189`。跨机器播放时，`MTX_WEBRTCADDITIONALHOSTS` 必须包含浏览器可访问的服务器 IP 或域名。

## 3. ai-stream 动态控制接口

### 3.1 启动算法推流任务

```http
POST /internal/v1/cameras/{cameraId}/tasks
Content-Type: application/json
X-Ai-Stream-Token: <token>
```

请求体：

```json
{
  "task": "deepsort",
  "inputUrl": "rtsp://admin:password@192.168.1.100:554/Streaming/Channels/101",
  "outputUrl": "rtsp://mediamtx:8554/live/camera_1_deepsort"
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `cameraId` | path number | 是 | 业务设备唯一编号；前端流名中的 `camera_{cameraId}` 应保持一致 |
| `task` | string | 是 | 必须存在于 `task_templates`，例如 `deepsort`、`boxmot` |
| `inputUrl` | string | 是 | 设备 RTSP 拉流地址；多个任务使用同一路输入时必须完全一致 |
| `outputUrl` | string | 是 | ai-stream 发布到 MediaMTX 的 RTSP 地址 |

成功响应 `200`：

```json
{
  "cameraId": 1,
  "active": true,
  "tasks": ["deepsort"]
}
```

curl 示例（宿主机调用 Docker 中的 ai-stream 时使用映射端口）：

```bash
curl -X POST http://127.0.0.1:19090/internal/v1/cameras/1/tasks \
  -H 'Content-Type: application/json' \
  -H 'X-Ai-Stream-Token: change-me-before-production' \
  -d '{"task":"deepsort","inputUrl":"rtsp://admin:password@192.168.1.100:554/Streaming/Channels/101","outputUrl":"rtsp://mediamtx:8554/live/camera_1_deepsort"}'
```

注意：`task` 必须是配置模板中的任务；未知任务返回 `400`。同一 `cameraId` 再次提交不同 `inputUrl` 会失败。重复提交相同任务和输出地址是幂等的。

### 3.2 查询摄像头任务状态

```http
GET /internal/v1/cameras/{cameraId}
X-Ai-Stream-Token: <token>
```

示例：

```bash
curl http://127.0.0.1:19090/internal/v1/cameras/1 \
  -H 'X-Ai-Stream-Token: change-me-before-production'
```

未启动时返回：

```json
{"cameraId":1,"active":false,"tasks":[]}
```

### 3.3 停止算法推流任务

```http
DELETE /internal/v1/cameras/{cameraId}/tasks/{task}
X-Ai-Stream-Token: <token>
```

```bash
curl -X DELETE http://127.0.0.1:19090/internal/v1/cameras/1/tasks/deepsort \
  -H 'X-Ai-Stream-Token: change-me-before-production'
```

删除最后一个任务后，ai-stream 会停止该摄像头的处理会话；MediaMTX 中对应算法路径也会因无发布者而不可读。

### 3.4 错误码

| HTTP 状态 | 含义 |
|---:|---|
| `200` | 操作成功 |
| `400` | JSON 无效、缺少字段、任务不存在或启动失败 |
| `401` | `X-Ai-Stream-Token` 缺失/错误（配置 token 非空时） |
| `404` | URL 路径不存在 |
| `405` | HTTP 方法不支持 |

## 4. MediaMTX 播放接口（WHEP）

### 4.1 播放地址规则

对 MediaMTX 的 HTTP 流地址追加 `/whep`：

```text
流基地址：http://<host>:8889/live/camera_1_deepsort/
WHEP接口：http://<host>:8889/live/camera_1_deepsort/whep
```

原始流同理：

```text
http://<host>:8889/live/camera_1/whep
```

### 4.2 浏览器获取画面的逐步过程

1. 前端先根据摄像头编号拼出算法流和原始流 URL。
2. 创建 `RTCPeerConnection({ iceServers: [] })`。
3. 添加接收器：`pc.addTransceiver('video', { direction: 'recvonly' })`。
4. 调用 `createOffer()`，并通过 `setLocalDescription()` 设置本地 SDP。
5. 等待 ICE gathering 完成（当前播放器最多等待 1 秒）。
6. 向 `{流URL}/whep` 发送 HTTP POST：

   ```http
   Content-Type: application/sdp
   Body: <pc.localDescription.sdp>
   ```

7. MediaMTX 返回 HTTP `200` 和 `Content-Type: application/sdp` 的 SDP answer。
8. 前端调用 `pc.setRemoteDescription({ type: 'answer', sdp: answer })`。
9. `pc.ontrack` 收到远端视频轨道，把 `event.streams[0]` 赋给 `video.srcObject`。
10. 设置 `<video autoPlay muted playsInline>` 并调用 `video.play()`，浏览器开始显示画面。
11. 前端等待首帧；超时、ICE failed/disconnected 或 3 秒无新帧时执行重连/降级。

### 4.3 最小可运行 JavaScript 示例

```js
async function playWhep(video, streamUrl) {
  const pc = new RTCPeerConnection({ iceServers: [] });
  pc.addTransceiver('video', { direction: 'recvonly' });
  pc.ontrack = (event) => {
    video.srcObject = event.streams[0] || new MediaStream([event.track]);
    video.play().catch(() => {});
  };

  const offer = await pc.createOffer();
  await pc.setLocalDescription(offer);
  await new Promise((resolve) => {
    if (pc.iceGatheringState === 'complete') return resolve();
    const timer = setTimeout(resolve, 1000);
    pc.onicegatheringstatechange = () => {
      if (pc.iceGatheringState === 'complete') {
        clearTimeout(timer);
        resolve();
      }
    };
  });

  const whepUrl = streamUrl.replace(/\/+$/, '') + '/whep';
  const response = await fetch(whepUrl, {
    method: 'POST',
    headers: { 'Content-Type': 'application/sdp' },
    body: pc.localDescription.sdp,
  });
  if (!response.ok) throw new Error(`WHEP HTTP ${response.status}`);
  await pc.setRemoteDescription({ type: 'answer', sdp: await response.text() });
  return pc; // 停止播放时调用 pc.close()
}
```

## 5. lanhu 当前前端实现对应关系

文件：`src/components/CenterPanel/components/MonitorGrid/MonitorGrid.jsx`

```js
const mediaBaseUrl = `${window.location.protocol}//${window.location.hostname}:8889/live`;
{
  primaryUrl: `${mediaBaseUrl}/camera_1_deepsort/`,
  fallbackUrl: `${mediaBaseUrl}/camera_1/`,
}
```

文件：`src/components/CenterPanel/components/MonitorGrid/WebRTCPlayer/webrtcPolicy.js`

- `buildWhepUrl(url)`：规范化 URL 并追加 `/whep`。
- 算法流连接超时：3 秒。
- 画面无新帧：3 秒判定卡死。
- 原始流下每 5 秒探测算法流。

因此新增设备时，至少要同步修改：

1. 后端启动接口的 `cameraId`、`inputUrl`、`outputUrl`。
2. 前端摄像头配置中的 `primaryUrl` 和 `fallbackUrl`。
3. 若使用新算法，`mtx/config.yaml` 或 `docker/docker-config.yaml` 的 `task_templates`、IPC 地址和 AI 服务必须存在。

## 6. 新增其他设备的标准步骤

### 步骤一：确认设备输入

用 ffplay/VLC 验证设备 RTSP 地址可读，并确认编码至少包含视频轨道：

```bash
ffprobe -rtsp_transport tcp '<设备RTSP地址>'
```

### 步骤二：准备任务模板

在 `task_templates` 增加任务名称和传输方式。需要把算法结果画回视频时使用 `shm`；只上报分析结果时使用 `base64`。启动对应 Python AI 服务并确认 IPC/TCP 地址可达。

### 步骤三：启动任务

为设备选择唯一 `cameraId`，按约定生成：

```text
原始路径：live/camera_{cameraId}
算法路径：live/camera_{cameraId}_{task}
```

调用 `POST /internal/v1/cameras/{cameraId}/tasks`。成功后等待 ai-stream 日志出现发布成功，再检查 MediaMTX 路径是否有流。

### 步骤四：验证 MediaMTX

先验证 RTSP 发布结果：

```bash
ffplay -rtsp_transport tcp rtsp://<host>:8554/live/camera_1_deepsort
```

再验证 WHEP 地址能返回 SDP（需要先准备一个有效浏览器 SDP offer，不能用普通 GET 代替）：

```text
POST http://<host>:8889/live/camera_1_deepsort/whep
Content-Type: application/sdp
```

### 步骤五：接入前端

把 `primaryUrl`、`fallbackUrl` 传给现有 `WebRTCPlayer`。不要把 `rtsp://...` 传给 `<video>`；浏览器只使用 `http(s)://<host>:8889/...` 的 WHEP 地址完成 WebRTC 协商。

### 步骤六：处理网络和生命周期

- 页面卸载或切换设备时调用 `RTCPeerConnection.close()`，清空 `video.srcObject`。
- MediaMTX `8889/tcp`、`8189/udp` 必须对浏览器网络可达。
- HTTPS 页面应使用 HTTPS WHEP；生产环境不要保留示例 token `change-me-before-production`。
- 不要把 `19090` 控制接口暴露到公网，前端通常应由业务后端代理调用。

## 7. 排查清单

1. `ai-stream` 是否运行，且控制端口 `19090` 可访问。
2. `inputUrl` 是否能从 ai-stream 所在容器/主机访问。
3. `outputUrl` 主机名：容器内应使用 `mediamtx:8554`，宿主机调用应使用映射地址。
4. MediaMTX 是否监听 `8554`、`8889`，Docker 是否映射 `8189/udp`。
5. `MTX_WEBRTCADDITIONALHOSTS` 是否包含浏览器可访问 IP。
6. 前端流路径是否与发布路径完全一致（包括 `live/` 前缀和任务名）。
7. 浏览器控制台是否出现 CORS、WHEP HTTP 404/500、ICE failed 或首帧超时。
