# llm_report_service 功能说明

本文说明监控事件报告生成服务（`Agent/llm_report_service`）的定位、扫描机制、报告生成流程、模型调用、配置与边界，供维护和联调时查阅。

## 1. 服务定位

`llm_report_service` 是一个常驻后台 Worker。它持续扫描数据库中新增的**事件片段**和**异常事件**，调用视觉大模型，把事件描述成一段中文监控报告，并把结构化结果写入 `llm_report` 表，供大屏和对话 Agent 查询。

处理两类对象：

| 来源表 | `prompt_type` | 说明 |
| --- | --- | --- |
| `episode` | `reid` | 轨迹合并后形成的事件片段，通常关联一个关注人员 |
| `vad` | `vad` | 视频异常检测记录（如烟火、越界） |

服务不提供 HTTP 接口，也不做行人检索。它**唯一写入的业务表是 `llm_report`**，其余表均为只读。

## 2. 运行形态与入口

| 项目 | 说明 |
| --- | --- |
| 入口 | `llm_report_service/main.py` |
| 形态 | 单进程、单线程轮询循环，无 Web 服务 |
| 启动脚本 | `Agent/scripts/start_report.sh`（`llm_report_service/start_*.sh` 为兼容旧路径的转发） |
| 解释器 | `Agent/.venv/bin/python` |
| 前置条件 | 模型接口已就绪；脚本会轮询 `/models`，等待 `LLM_MODEL_ID` 出现在模型列表中，最长 `LLM_STARTUP_TIMEOUT_S`（默认 300 秒） |
| 退出 | 无自动退出条件，随容器/终端生命周期运行 |

`start_report.sh` 读取 `Agent/.env`，把最终的模型、数据库、扫描参数以命令行参数显式传给 `main.py`，再 `exec` 启动。`LLM_MODE=api` 时同样直接连接远端兼容接口。

## 4. 扫描与调度

### 4.1 启动阶段

1. 打印 `llm_backend`、`llm_model`、`llm_base_url`。
2. 记录当前 `episode` 与 `vad` 总行数（`episode_total`、`vad_total`）。
3. 若指定 `--backfill-existing`，先按 `batch_size` 循环清空**全部**待处理 `vad`，再清空全部待处理 `episode`，完成后进入常规循环。

### 4.2 常规循环

| 周期 | 动作 |
| --- | --- |
| 每 10 秒（固定） | 比较 `vad` 总数；增长时按 `offset` 分页处理新增行；再查询近 `RECENT_PENDING_HOURS`（默认 1 小时）内仍缺报告的 `vad` 补跑 |
| 每 `SCAN_INTERVAL_S`（默认 60 秒） | 比较 `episode` 总数；增长时按 `offset` 分页处理新增行；再查询近期仍缺报告的 `episode` 补跑 |

设计要点：

- **只处理近期数据**：非补跑模式下，早于 `now - RECENT_PENDING_HOURS` 的事件直接跳过（`skip historical ...`）。补跑全部历史必须显式加 `--backfill-existing`。
- **按总数增量分页**：以「上次总数」作为 `offset`，按 `start_ts, id`（`vad` 按 `id`）顺序翻页。该方式假设新行追加在末尾；乱序插入造成的漏处理由「近期 pending 查询」兜底。
- **失败不阻塞**：单条处理异常只打印 `failed ...` 和堆栈，循环继续；下轮 pending 查询会再次拾起。
- **串行处理**：没有并发池，一条包含多段视频的报告会阻塞后续事件。

### 4.3 去重

报告写入前先查 `llm_report` 是否已存在 `(episode_id, prompt_type)` 或 `(vad_id, prompt_type)` 记录；存在即跳过。`save_llm_report` 内部也会再查一次，避免并发重复插入。这使 Worker 重启、重复扫描都是幂等的。

## 5. 单条报告生成流程

### 5.1 episode

1. 校验时间窗口（`should_process`），检查是否已有 `reid` 报告。
2. 读取主轨迹：`episode_tracklet_link` 中按 `created_at, id` 取第一条关联的 `tracklet`。
3. 解析人员姓名：
   - 优先取 `episode.meta.stranger_target_id`，否则取 `tracklet.stranger_target_id`；
   - 用该 ID 查 `stranger_target.code`，统一为 `STR-` 编号：已带 `STR-` 前缀原样保留，纯数字补零为 `STR-001`，其他值加前缀；
   - 编号存在时覆盖 `person.name`。
4. 选择媒体：优先 `episode_media_link` 关联的 `media_asset`，仅取 `asset_type in ('clip','segment')`，按与事件时间窗的重叠时长降序，最多 `MEDIA_LIMIT`（默认 2）条；无关联时按 `stream_id` + 时间重叠回退查询。
5. 组装语义输入并生成报告。

### 5.2 vad

1. 校验时间窗口，检查是否已有 `vad` 报告。
2. 按 `vad.media_asset_id` 读取唯一媒体素材。
3. 语义输入以 `vad.created_at` 作为时间范围，携带 `anomaly_name`、`anomaly_level` 和 `frame_vad_base64` 异常帧。
4. 生成报告。

### 5.3 语义输入结构

`EpisodeSemanticInput` 统一序列化为 JSON：

```json
{
  "episode_id": "...",
  "time_range": {"start": "...", "end": "..."},
  "camera_id": 3,
  "person": {"name": "张三", "image_base64": "..."},
  "trajectory": {"color_rgb": [255, 0, 0], "points": [[x, y], ...], "point_count": 128},
  "media": [{"type": "video", "path": "...", "start_ts": "...", "duration_ms": 5000, "asset_type": "clip"}]
}
```

- `camera_id`、`person_name`、`person_image` 优先取 `episode.meta`，缺失时用主轨迹的 `color_rgb`、`trajectory_points`、`query_asset_base64` 补齐。
- 轨迹点超过 64 个时等间隔采样，`point_count` 保留原始数量。
- 序列化时超过 512 字符的字符串（如 Base64）替换为 `[omitted len=N]`，避免 JSON 提示词膨胀。
- VAD 的 `person` 中额外带 `anomaly_name`、`anomaly_level`，`camera_id` 为 `null`。

### 5.4 多模态消息

`build_remote_multimodal_content` 按以下顺序拼装一条 `HumanMessage` 的内容块：

1. `PersonSnapshot:` + 人员截图（Data URL）；
2. 每段视频：抽取 `MAX_VIDEO_FRAMES`（默认 8）帧，每帧前置 `Video{n}-Frame{m}:` 标签；
3. 视频无法读取时退化为一条文本 `Video{n}-PATH: <原始路径>`；
4. 最后是用户提示词，内含语义输入 JSON 和输出格式说明。

图片统一转为 RGB，长边不超过 1280，JPEG 质量 88，再编码为 Data URL。视频帧由 `decord` 在整段视频内均匀采样。

### 5.5 模型调用与结果解析

- 调用 `llm.invoke([SystemMessage(REPORT_SYSTEM), HumanMessage(content)], response_format=json_schema)`，长度上限在请求体中体现为 `max_tokens`（默认 1024）。
- 只接受 `_llm_type` 为 `sglang_openai` 或 `vllm_openai` 的客户端，其他类型直接报错。
- 远端返回 OOM（错误文本含 `out of memory` / `cuda oom`）且 `oom_fallback_text_only=True` 时，丢弃全部图片，仅用文本语义输入重试一次，`max_new_tokens=128`。
- 响应解析顺序：去掉 Markdown 代码围栏 → 截取首个 `{` 到最后一个 `}` → `json.loads`，失败再用 `ast.literal_eval`。
- 用 `ReportOutput` 校验并归一化，不符合结构时抛异常，本条记 `failed`，不写库。

### 5.6 落库

`save_llm_report` 插入 `llm_report`：

| 字段 | 值 |
| --- | --- |
| `id` | 新 UUID |
| `episode_id` / `vad_id` | 二者只填其一 |
| `prompt_type` | `reid` 或 `vad` |
| `report_json` | 结构化报告（jsonb） |
| `report_text` | 等于 `summary` |
| `created_at` | 当前 UTC 时间 |

成功打印 `saved llm_report for episode=...` / `vad=...`。

## 6. 报告结构

`ReportOutput` 定义并校验以下字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `event_type` | string | 事件类型 |
| `summary` | string | 中文自然语言描述，同时作为 `report_text` |
| `risk_level` | `low` / `medium` / `high` | 风险等级 |
| `key_observations` | string[] | 关键观察点 |
| `confidence` | number | 置信度 |

提示词要求模型只输出 JSON、`risk_level` 取枚举值、`confidence` 在 0～1、有姓名时在摘要或观察点中体现，并且**不要输出坐标和轨迹颜色**。

## 7. 模型客户端与配置解析

### 7.1 共享配置

`llm/settings.py` 在导入时加载 `Agent/.env`（不覆盖已有环境变量），再执行 `resolve_model_settings`：

- `LLM_MODE=local`：使用 `LLM_LOCAL_*` → `LLM_*` → 后端专属变量，默认本地 `http://127.0.0.1:8000/v1`。
- `LLM_MODE=api`：强制使用 `LLM_REMOTE_BASE_URL`、`LLM_REMOTE_MODEL_ID`、`LLM_REMOTE_API_KEY`，缺失或地址带 `/chat/completions`、内嵌凭据时直接报错，**不会回退到本地地址**。
- `LLM_HEALTHCHECK`：`auto`（本地模式查 `/models`，API 模式跳过）、`models`、`none`。
- `LLM_REMOTE_RESPONSE_FORMAT`：`json_schema`（透传完整 Schema）、`json_object`（降级为 `{"type":"json_object"}`）、`none`（移除该字段）。

Agent 服务复用同一份解析逻辑，因此两个服务的模型行为保持一致。

### 7.2 ChatSGLang / ChatVLLM

- 直接请求 `{base_url}/chat/completions`，`Authorization: Bearer <api_key>`。
- 默认 `temperature=0.0`，`max_tokens` 取调用参数或配置值。
- `enable_thinking` 为 `None` 时不发送 `chat_template_kwargs`，由服务端默认决定；显式布尔值才写入。
- 重试：`429/502/503/504` 与超时、传输错误最多重试 `LLM_MAX_RETRIES` 次，退避 `min(0.5 × 2^n, 2s)`；其他 4xx/5xx 立即失败。
- 流式接口同样可用（`_stream`），当前报告生成只用非流式。
- `check_health()` 只查 `/models`，不发起计费聊天请求。

## 8. 配置项

`.env` 经 `start_report.sh` 转为命令行参数，主要项如下：

| 变量 / 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `LLM_MODE` | `local` | `local` 本地引擎，`api` 远端接口 |
| `LLM_BACKEND` / `--llm-backend` | `sglang` | `sglang` 或 `vllm` |
| `LLM_BASE_URL` / `--llm-base-url` | `http://127.0.0.1:8000/v1` | 聊天接口根地址 |
| `LLM_MODEL_ID` / `--llm-model` | `internvl3.5-8b` | 模型名，需与 `/models` 返回一致 |
| `LLM_API_KEY` / `--llm-api-key` | `unused` | 接口密钥 |
| `LLM_CONNECT_TIMEOUT_S` / `LLM_REQUEST_TIMEOUT_S` | `5` / `180` | 连接与请求超时 |
| `LLM_MAX_RETRIES` | `2` | 重试次数 |
| `LLM_MAX_NEW_TOKENS` / `--max-new-tokens` | `1024` | 报告最大生成长度 |
| `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME` / `DB_SCHEMA` | `100.127.237.7` / `5432` / `root` / — / `postgres` / `public` | 数据库连接 |
| `SCAN_INTERVAL_S` / `--scan-interval-s` | `60` | episode 扫描周期 |
| `BATCH_SIZE` / `--batch-size` | `8` | 每批处理条数 |
| `MEDIA_LIMIT` / `--media-limit` | `2` | 每个 episode 的视频段数上限 |
| `MAX_VIDEO_FRAMES` / `--max-video-frames` | `8` | 每段视频抽帧数 |
| `MEDIA_BASE_DIR` / `--media-base-dir` | `/home/guest/Documents/lkh/mtx/mediamtx` | 相对媒体路径的根目录 |
| `RECENT_PENDING_HOURS` / `--recent-pending-hours` | `1` | 补跑窗口；为负会报参数错误 |
| `--backfill-existing` | 关闭 | 显式补跑全部历史缺失报告 |

`start_report.sh` 已透出上表全部参数；`--backfill-existing` 通过脚本末尾的 `"$@"` 追加，例如 `./scripts/start_report.sh --backfill-existing`。`ServiceConfig` 另有 `oom_fallback_text_only=True` 与 `oom_retry_max_new_tokens=128`，目前不可通过命令行关闭。

## 9. 数据表依赖

| 表 | 读写 | 用途 |
| --- | --- | --- |
| `episode` | 读 | 事件片段、时间范围、`meta` |
| `episode_tracklet_link` | 读 | 事件与轨迹关联 |
| `tracklet` | 读 | 主轨迹的颜色、轨迹点、查询图、陌生人 ID |
| `episode_media_link` | 读 | 事件与媒体关联 |
| `media_asset` | 读 | 视频路径、时长、类型 |
| `stranger_target` | 读 | 陌生人编号 |
| `vad` | 读 | 异常事件、异常帧 |
| `llm_report` | 读写 | 报告去重与写入 |

兼容处理：当 `media_asset` 没有 `play_url` 列时，自动回退到 `path` 列，两种查询各有一套 SQL，不修改数据库结构。

## 10. 日志与运行输出

当前以标准输出为主，无结构化事件日志：

- 启动：`llm_backend=... llm_model=... llm_base_url=...`、`episode_total=N`、`vad_total=N`；
- 增量：`episode_total_grew A -> B`、`vad_total_grew A -> B`；
- 单条：`saved llm_report for episode=...` / `vad=...`；
- 失败：`failed episode=...` / `failed vad=...` 加完整堆栈；
- 媒体读取失败：`读取视频帧失败，路径=...，错误=...`。

`utils/log.py` 提供的 `setup_logging` 目前未被 `main.py` 调用。排查时建议同时对照 Agent 服务 `agent.jsonl` 中对该报告的引用，以及 `llm_report.created_at` 的时间分布。

## 11. 已知边界与注意事项

- **串行吞吐有限**：一条事件最多 2 段视频 × 8 帧 + 1 张人员图，视觉请求较慢时会推迟后续事件。
- **失败重试靠轮询**：模型输出格式错误、媒体损坏等异常不会重试同一事件，而是等下一轮 pending 查询再次处理；持续失败的事件会反复进入日志。
- **默认不补历史**：超过 `RECENT_PENDING_HOURS` 的缺失报告不会自动生成；需要时显式使用 `--backfill-existing`，该模式会长时间占用 Worker。
- **VAD 轮询固定 10 秒**，与 `SCAN_INTERVAL_S` 无关，无法通过配置调整。
- **增量计数依赖追加顺序**：`offset = 上次总数` 的分页方式在乱序插入时可能跳过记录，由 pending 查询兜底；如底层写入大量乱序，应关注 pending 是否及时清空。
- **OOM 回退会丢图**：文本-only 重试只保留语义 JSON，报告将缺少视觉依据，`confidence` 可能偏低。
- **媒体路径必须在 Worker 主机可读**：相对路径基于 `MEDIA_BASE_DIR` 解析；`http(s)://` 路径原样传给抽帧器（当前 `decord` 只接受本地文件，远程 URL 会退化为文本路径提示）。
- **模型输出不可信**：所有响应都经 JSON 提取与 `ReportOutput` 校验后才入库，但报告内容仍属模型推断，不是事实判定。
- **无鉴权、无 HTTP 面**：服务只访问数据库和模型接口，部署时需保证网络可达且凭据不落库。
- **不做数据库迁移**：表结构需由外部初始化。`Agent/sql/database.sql` 含 `DROP TABLE`，仅用于结构核对，不能作为初始化脚本执行。
