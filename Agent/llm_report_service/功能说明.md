# llm_report_service 功能说明（智慧监控大屏 · 大模型自动生成监控报告）

## 1. 服务定位

`llm_report_service` 是智慧监控系统中的**大模型自动报告生成服务（离线/准实时 Worker）**，主要职责是：

- 以 **PostgreSQL（+ pgvector）** 为数据中心，消费算法侧写入的结构化事件数据（`episode`）与异常数据（`vad`）
- 从数据库关联抽取轨迹、关键帧（base64）、媒体片段索引（`media_asset`）等证据
- 通过 LangChain 调用 **SGLang 中部署的 InternVL 多模态大模型**（可读行人截图 + 视频关键帧）生成**结构化监控报告**
- 将报告以 `jsonb + text` 的形式写回 PostgreSQL 的 `llm_report` 表，供前端大屏/系统后端/检索服务查询展示

该服务在系统架构中充当“**语义总结与报告中台**”：将算法输出的低层时空信息转化为适合业务理解与展示的文本/结构化结论。


## 2. 运行形态与入口

- **入口脚本**：`llm_report_service/main.py`
- **运行方式**：常驻进程（循环扫描 + 增量处理），非 HTTP API 服务
- **处理对象**：
  - `episode`：行为事件容器（通常来自 ReID/轨迹聚合/事件切分）
  - `vad`：异常检测记录（跌倒/打架/火灾等）

### 2.1 扫描与增量策略（核心逻辑）

`main.py` 通过以下策略保证“**不重复、可恢复、准实时**”：

- 启动时：
  - 优先补跑 `fetch_pending_vads / fetch_pending_episodes`（即 DB 中缺少 `llm_report` 的记录）
- 运行中：
  - 周期性检查 `vad` 总数是否增长（每 10s），有增长则按 offset 分批处理
  - 周期性检查 `episode` 总数是否增长（默认每 60s，可配置），有增长则按 offset 分批处理
  - 兜底：每轮额外补跑一次 `fetch_pending_episodes`，避免乱序写入导致漏处理

用于去重的关键约束是：`llm_report` 中以 `(prompt_type, episode_id)` 或 `(prompt_type, vad_id)` 判断是否已生成。


## 3. 核心模块与职责

### 3.1 配置（`config.py`）

- `DbConfig`：PG 连接信息（host/port/user/password/database/schema/driver）
- `ModelConfig`：SGLang 地址、模型名、超时、重试和生成参数
- `ServiceConfig`：
  - `scan_interval_s`：episode 扫描间隔
  - `batch_size`：批处理大小
  - `media_limit`：每个 episode 最多取几个视频片段参与多模态理解
  - `max_video_frames`：每个视频片段采样帧数
  - `media_base_dir`：媒体文件本地根目录（用于拼接 `media_asset.path`）
  - `oom_fallback_text_only`：OOM 时回退文本模式


### 3.2 DB 访问层（`db/*_repo.py`）

- `episode_repo.py`
  - `fetch_pending_episodes`：查询“缺报告”的 episode
  - `fetch_primary_tracklet`：从 `episode_tracklet_link` 找到 episode 的主轨迹（用于轨迹点/行人截图/stream_id）

- `vad_repo.py`
  - `fetch_pending_vads`：查询“缺报告”的 VAD 记录

- `media_repo.py`
  - `select_episode_media`：优先从 `episode_media_link` 选 clip/segment；无关联则按 `stream_id + 时间重叠度` 兜底检索
  - `get_media_asset_by_id`：用于 VAD 场景

- `report_repo.py`
  - `has_llm_report`：去重检查
  - `save_llm_report`：写入 `llm_report`（`report_json` cast 为 `jsonb`，`report_text` 用于摘要检索/展示）

- `stranger_repo.py`
  - `get_stranger_code`：当 episode 对应陌生人时，从 `stranger_target` 取编号，覆盖 `person.name`（如 `STR-001`）


### 3.3 语义输入构建（`service/episode_builder.py`）

将 DB 行数据归一化成“给大模型看的结构化输入” `EpisodeSemanticInput`：

- `time_range`：事件起止
- `person`：
  - `name`（可被陌生人编号覆盖）
  - `image_base64`（优先从 episode.meta，其次从 tracklet.query_asset_base64）
- `trajectory`：
  - `color_rgb`（轨迹/检测框颜色，优先 meta，其次 tracklet.color_rgb）
  - `points`（轨迹点，采样到最多 64 点）
- `media`：视频片段列表（path/start_ts/duration_ms/type 等）

VAD 场景使用 `build_vad_semantic_input`：将异常类型/等级与异常帧（`frame_vad_base64`）封装进同一语义结构。


### 3.4 报告生成执行器（`service/report_runner.py`）

核心步骤：

1. **多模态输入拼装**
   - PersonSnapshot：行人截图由 base64 解码为 PIL 图片
   - Video frames：对每个 `media_asset.path` 指向的视频文件用 `decord` 在 CPU 上采样 `max_video_frames` 帧
   - 远程 SGLang 模式将图片缩放、压缩为 JPEG data URL，拼装成 OpenAI 兼容的 `text + image_url` 内容块

2. **Prompt 构造**（`llm/prompt.py`）
   - 系统提示 `REPORT_SYSTEM`：强调轨迹颜色、轨迹点、关键帧证据
   - 用户模板 `REPORT_USER_TEMPLATE`：要求**严格输出 JSON**，并包含风险等级、置信度、关键观察点等

3. **模型调用**
   - 默认由 `llm/sglang_model.py` 的 `ChatSGLang` 实现 LangChain `BaseChatModel`
   - 通过 SGLang OpenAI 兼容接口 `/v1/chat/completions` 调用已经加载的模型
   - 使用持久化 HTTP 连接、连接/请求超时和有限重试

4. **解析与规范化**
   - SGLang 请求携带 `response_format=json_schema`，要求模型按 `ReportOutput` Schema 输出
   - 从模型输出中抽取 JSON
   - 使用 `pydantic` 校验并归一化字段：`event_type/summary/risk_level/key_observations/confidence`

5. **OOM 兜底**
   - SGLang 返回远程 CUDA OOM 时，可去掉多模态输入仅用文本重试，并降低 `max_new_tokens`


## 4. 以 PostgreSQL 为中心的数据闭环（与其他子系统交互）

### 4.1 与算法服务端的关系

- **算法侧负责写入事实与证据**：
  - `tracklet`：轨迹、关键帧、轨迹点、（可选）embedding（pgvector）
  - `episode`：事件切分/聚合结果（meta 内包含 person_name、trajectory_points 等）
  - `episode_tracklet_link`：事件与轨迹关联
  - `vad`：异常检测结果与异常帧
  - `media_asset`：可回放视频片段索引（path/start_ts/duration_ms）

- **llm_report_service 负责写入语义报告**：
  - `llm_report.prompt_type='reid'`：面向 episode（人员行为/轨迹相关事件）
  - `llm_report.prompt_type='vad'`：面向 vad（异常事件）


### 4.2 与前端大屏的关系

- 前端通常不直接消费算法原始表，而是优先消费 `llm_report.report_text` 或 `llm_report.report_json`，以便：
  - 直接展示“事件摘要/风险等级/关键观察点”
  - 结合 `episode`/`tracklet` 提供的回放与关键帧证据进行可视化


### 4.3 与流媒体/回放后端的关系

该服务本身不生成回放 URL，也不代理视频流；它做的是：

- 通过 `media_asset.path` 找到本地/挂载的视频文件路径（`media_base_dir + path`）
- 对视频文件采样关键帧，提供给多模态模型做理解

回放 URL 的生成一般由“聊天服务/检索服务/前端”根据 `media_asset` 的时间索引与流 ID 来拼接。


### 4.4 与系统后端（业务管理）的关系

- 系统后端负责摄像头/任务实例/人员库/陌生人库等配置与管理
- 这些配置影响算法写入的 `episode/meta`、`stranger_target.code` 等，从而影响报告中的 person 名称与描述


## 5. 关键数据表与字段（计划书抽象）

该服务直接读写的关键表：

- `episode`：事件容器（时间范围 + meta）
- `episode_tracklet_link`：事件-轨迹关联
- `tracklet`：轨迹、关键帧（base64）、轨迹点（jsonb）、可选向量（pgvector）
- `vad`：异常记录（含异常帧 base64、异常类型/等级、媒体关联）
- `media_asset`：媒体片段索引（start_ts/duration_ms/path）
- `episode_media_link`：事件与媒体关联
- `llm_report`：大模型报告（report_json jsonb + report_text 摘要）
- `stranger_target`：陌生人编号（用于报告中替代真实姓名）

关于“PostgreSQL 能存 torch”：当前实现更多体现为

- 视觉证据：`image_base64` / `frame_vad_base64` 等（文本形式）
- 向量特征：使用 `pgvector vector(N)` 存储 embedding（可视作 torch tensor 的数据库化表达，便于检索与关联）


## 6. 输出报告格式（面向大屏）

`llm_report_service` 输出的结构化报告由 `pydantic` 约束，核心字段：

- `event_type`：事件类型（模型生成）
- `summary`：中文摘要（尽量详细）
- `risk_level`：`low | medium | high`
- `key_observations`：要点列表
- `confidence`：0.0~1.0

最终写入：

- `llm_report.report_json`（jsonb）：结构化内容
- `llm_report.report_text`（text）：通常取 `summary`，方便检索与直接展示


## 7. 部署与配置

### 7.1 启动模型和报告 Worker

同一台服务器运行 SGLang 和 Worker 时，先在一个终端启动模型：

```bash
cd /data1/wangzj/InternVL3.5-8B

CUDA_VISIBLE_DEVICES=3 ./scripts/start_sglang.sh
```

再在另一个终端启动报告 Worker：

```bash
cd /data1/wangzj/InternVL3.5-8B
DB_HOST=<PG_HOST> \
DB_USER=<PG_USER> \
DB_PASSWORD=<PG_PASSWORD> \
DB_NAME=<PG_DB> \
MEDIA_BASE_DIR=/path/to/mediamtx \
./scripts/start_report.sh
```

`start_report.sh` 只等待 `LLM_BASE_URL` 上的模型接口就绪，再启动报告 Worker；它不会启动或停止 SGLang。若还需要 Agent，可使用 `./scripts/start_all.sh` 一次启动完整服务，由该入口管理模型进程。完整入口启动 SGLang 时，日志默认写入 `.runtime-cache/llm-report-service/sglang.log`。

常用环境变量：

模型相关参数从仓库根目录 `.env` 读取；以下模型环境变量仅在需要临时覆盖 `.env` 时设置：

```bash
LLM_BASE_URL=http://127.0.0.1:8000/v1
LLM_MODEL_ID=internvl3.5-8b
LLM_API_KEY=unused
REPORT_PYTHON_BIN=/data1/userhome/va/miniconda3/envs/monitor/bin/python
LLM_STARTUP_TIMEOUT_S=300
```

使用其他服务器上的 SGLang 时，脚本只启动本地 Worker：

```bash
LLM_BASE_URL=http://192.168.96.201:8000/v1 \
LLM_MODEL_ID=internvl3.5-8b \
LLM_API_KEY=<API_KEY> \
./scripts/start_report.sh
```

### 7.2 单独启动 SGLang

先在项目根目录启动模型服务：

```bash
cd /data1/wangzj/InternVL3.5-8B
./scripts/start_sglang.sh
```

默认服务地址为 `http://127.0.0.1:8000/v1`，对外模型名为 `internvl3.5-8b`。脚本支持通过环境变量覆盖 GPU、端口和显存比例，例如：

```bash
CUDA_VISIBLE_DEVICES=3 \
SGLANG_PORT=8000 \
SGLANG_MEM_FRACTION_STATIC=0.80 \
./scripts/start_sglang.sh
```

可以在另一个终端检查服务是否可用：

```bash
curl http://127.0.0.1:8000/v1/models
```

### 7.3 单独启动报告 Worker

```bash
/data1/userhome/va/miniconda3/envs/monitor/bin/python \
  llm_report_service/main.py \
  --llm-backend sglang \
  --llm-base-url http://127.0.0.1:8000/v1 \
  --llm-model internvl3.5-8b \
  --llm-request-timeout-s 180 \
  --llm-max-retries 2 \
  --db-host <PG_HOST> \
  --db-port 5432 \
  --db-user <PG_USER> \
  --db-password <PG_PASSWORD> \
  --db-name <PG_DB> \
  --db-schema public \
  --scan-interval-s 60 \
  --batch-size 8 \
  --media-limit 2 \
  --max-video-frames 8 \
  --media-base-dir /path/to/mediamtx
```

SGLang 与报告 Worker 可以使用不同 Conda 环境。Worker 仅通过 HTTP 调用 SGLang，不需要激活或修改 `/home/zwd/miniconda3/envs/sglang`。

### 7.4 依赖要点

`requirements.txt` 包含：`httpx`、`decord`、`sqlalchemy`、`psycopg2-binary/pg8000`、`langchain-core` 等。Worker 通过 HTTP 调用 SGLang，不加载模型权重；`decord` 用于 CPU 视频抽帧。

安装或刷新 Worker 依赖：

```bash
/data1/userhome/va/miniconda3/envs/monitor/bin/python -m pip install \
  -r llm_report_service/requirements.txt
```

模型切换参数集中在仓库根目录 `.env`，操作步骤见 [模型切换说明](../MODEL_SWITCHING.md)。


## 8. 计划书可用的亮点表述（建议写法）

- **“事件->报告”的自动化闭环**：算法产出 episode/vad（事实与证据），大模型产出可读报告（语义与风险），并统一入库。
- **多模态证据驱动的可解释报告**：报告不是纯文本“编造”，而是结合行人截图与视频关键帧生成，支撑大屏可视化与复核。
- **结构化输出，面向业务集成**：`jsonb` 报告天然适合前端直接渲染、后端检索统计、后续二次分析。
- **高可用与成本可控**：增量扫描 + 去重 + OOM 回退机制，适合在边缘 GPU 或中心 GPU 节点持续运行。


## 9. 已知边界与后续扩展点

- **触发方式可升级**：当前是轮询扫描，后续可接入消息队列/CDC（更实时、降低 DB 压力）。
- **吞吐可继续提升**：当前 Worker 顺序处理数据库记录；确认数据库连接与任务幂等策略后，可增加有界并发以利用 SGLang 的连续批处理能力。
- **请求体需要持续约束**：当前会缩放和压缩帧图片；媒体数量或采样帧数继续提高时，建议增加单请求图片总数和字节数上限。
- **回放与证据统一**：目前仅做本地视频采样；后续可与回放服务做统一的“片段索引/证据快照”策略。
- **报告质量与模板化**：可按不同场景（入侵/徘徊/跌倒等）引入更细粒度 prompt 模板与评测闭环。
- **权限与审计**：面向生产化可引入报告生成审计、人工复核状态、策略阈值等。
