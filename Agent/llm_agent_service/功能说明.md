# llm_agent_service 功能说明（智慧监控大屏 · 大模型对话服务）

## 1. 服务定位

`llm_agent_service` 是智慧监控系统“大屏展示”场景下的**大模型对话编排服务**：

- 以 **PostgreSQL（+ pgvector）** 为数据中心，读取算法侧写入的结构化结果（人员库、轨迹、异常、事件报告等）。
- 对前端提供统一的 `/chat` 接口：用户用自然语言（可带图片）提问，服务根据规则路由到合适的数据查询与大模型总结逻辑。
- 输出面向大屏渲染的结构化 JSON（包含摘要、关键帧 base64、回放 URL、统计信息等），便于前端直接展示。

该服务目前实现为“**规则路由 + 数据检索 + LLM 总结**”，不是通用 ReAct/Tool Agent（仓库内旧 README 中提到的 ReAct 工具注册在当前目录代码中并不存在，以本说明文档为准）。


## 2. 运行形态与入口

- **入口脚本**：`llm_agent_service/main.py`
  - 解析启动参数（DB、模型、时区、回放服务地址等）
  - 创建 PostgreSQL SQLAlchemy Engine：`llm_agent_service/db/session.py#create_pg_engine`
  - 构建多模态 LLM：`llm_agent_service/llm/__init__.py -> llm_report_service.llm.factory#build_chat_model`
  - 启动 Flask：`llm_agent_service/app.py#create_app`

- **HTTP 服务**：Flask（默认端口 `8002`）
- **并发**：Flask `threaded=True`，`ReidService` 内部使用锁保护“熟人列表”缓存


## 3. 核心模块与职责

### 3.1 Flask API（`app.py`）

对外提供：

- `POST /chat`
  - 输入：`prompt`（必填）+ `session_id`（可选）+ 可选图片（base64 或文件上传）
  - 输出：结构化 JSON（见第 6 节）
  - 兼容：
    - `application/json`：`{"prompt": "...", "image": "<base64>"}`
    - `multipart/form-data`：`prompt=<text>` + `file=@xxx.jpg` 或 `image=<base64>`

- `POST /reload_persons`
  - 作用：手动触发熟人库缓存刷新（从 `reid_target` 重新加载）

- `GET /persons`
  - 作用：返回当前缓存的熟人列表（name -> person_ids）

- `GET /health`
  - 作用：Flask 进程存活检查，不访问外部依赖

- `GET /ready`
  - 作用：检查 PostgreSQL 和 SGLang `/v1/models`
  - 数据库或模型服务不可用时返回 HTTP 503

- `DELETE /sessions/<session_id>/memory`
  - 作用：清空指定会话的进程内消息历史

其他特性：

- **CORS**：优先使用 `flask-cors`，缺失则回退为手动 CORS 头
- **中文 JSON**：`ensure_ascii=False`，保证前端直接可读


### 3.2 规则路由与业务编排（`service/reid_service.py`）

`ReidService.process(prompt, image_base64)` 负责根据用户输入决定走哪条主流程：

- **异常查询（VAD）**：当 `prompt` 包含关键词 `"异常"`
- **熟人/人员查询（ReID）**：当 `prompt` 中包含任一熟人姓名（熟人名单来自 DB 的 `reid_target.is_active=true`）
- **普通问答**：否则直接调用多模态/文本 LLM 回复

同时支持：

- **自然语言时间解析**：支持今天/昨天/前天/具体年月日/xx月xx日等
- **图片辅助问答**：若传入图片，会先进行图像理解并拼接到业务回答前
- **大模型总结**：对多条报告/异常报告做聚合总结（控制字数）
- **回放 URL 生成**：按轨迹/异常记录构造流媒体回放链接
- **会话记忆**：相同 `session_id` 的普通问答会携带最近的 LangChain 消息历史

### 3.3 会话记忆（`service/memory.py`）

- 使用 `langchain_core.chat_history.InMemoryChatMessageHistory`
- 默认最多保留 1000 个会话，每个会话保留最近 20 条消息（约 10 轮）
- 会话通过 `session_id` 隔离，同一会话的并发请求串行执行
- 未提供 `session_id` 时由 `/chat` 自动生成，并随响应返回
- 图片只记录“用户上传了一张图片”的文本标记，不保存 base64 内容
- 当前为单进程内存记忆，服务重启后丢失，多实例之间不共享

### 3.4 多模态 LLM（LangChain + SGLang）

- 默认复用 `llm_report_service.llm.factory.build_chat_model()` 创建 `ChatSGLang`
- 文本调用使用 LangChain `BaseChatModel.invoke()`
- 图片输入：base64 -> PIL -> 压缩 JPEG data URL -> OpenAI `image_url` 内容块
- SGLang 模型服务负责加载 InternVL 和执行 GPU 推理，Agent Flask 进程不加载模型权重


## 4. 以 PostgreSQL 为中心的数据闭环（系统交互）

该服务自身主要是**读** PostgreSQL（并做汇总与链接生成），核心依赖“其他系统把数据写入 PG”。典型闭环如下：

- **算法服务端（检测/跟踪/ReID/VAD/事件分析）**
  - 产出：轨迹 `tracklet`、异常 `vad`、事件 `episode/llm_report`、人员库 `reid_target/stranger_target`、媒体索引 `media_asset`
  - 写入：PostgreSQL（包含 pgvector embedding、jsonb 轨迹点、关键帧 base64 等）

- **流媒体/回放后端**
  - 提供：`GET /get?path=<...>&start=<...>&duration=<...>` 形式的回放能力
  - `llm_agent_service` 在响应中返回该 URL，前端直接播放

- **前端大屏**
  - 调用：`POST /chat`
  - 渲染：
    - `summary`（一句话总结）
    - `tracklet` 统计（各摄像头次数）
    - `data.trackletN.image`（base64 关键帧）
    - `data.trackletN.recording`（回放 URL）

- **系统后端（业务管理/配置）**
  - 管理：摄像头、流/任务实例（`camera/camera_stream`）、人员库（`reid_target`）等
  - 通过 DB 更新后，`llm_agent_service` 可自动刷新熟人缓存（默认每 60 秒轮询）或通过 `/reload_persons` 手动刷新


## 5. 关键数据表与字段（面向计划书的抽象）

> 代码中访问到的表主要包括：`reid_target`、`tracklet`、`episode`、`episode_tracklet_link`、`llm_report`、`vad`、`camera_stream`、`camera`、`media_asset`。
> 其中 embedding 使用 `pgvector` 的 `vector(N)` 类型（用于存储行人特征等，可视作“torch 特征向量”的数据库化表达）。

- **人员库（内部人员）**：`reid_target`
  - `id (uuid)`：人员ID
  - `name (text)`：姓名/别名
  - `is_active (bool)`：是否启用（被用于加载熟人列表）
  - `image_base64 (text)`：人员底库图（用于展示/复核/再提特征）
  - `embedding (vector(N))`：底库特征向量（pgvector）

- **轨迹（核心实体）**：`tracklet`
  - `id (uuid)`：轨迹ID
  - `stream_id (uuid or text)`：所属流/任务实例（关联 `camera_stream`）
  - `start_ts/end_ts (timestamptz)`：轨迹起止时间
  - `gallery_target_id (uuid)`：命中内部人员时关联的 `reid_target.id`
  - `query_asset_base64/frame_asset_base64 (text)`：关键帧（当前实现直接按 base64 字段读取/返回）
  - `trajectory_points (jsonb)`：轨迹点序列（用于可视化或行为分析）
  - `repr_embedding (vector(N))`：轨迹级代表特征（pgvector）

- **事件与报告**：`episode` + `episode_tracklet_link` + `llm_report`
  - `episode`：事件容器（一个事件可能包含多条轨迹）
  - `llm_report.report_json/report_text`：LLM 结构化分析结果/可读摘要
  - `llm_report.vad_id`：在异常场景下可直接挂到某条 `vad` 记录

- **异常（VAD）**：`vad`
  - `id (int)`、`created_at`、`stream_id`、`media_asset_id`
  - `frame_vad_base64`：异常帧关键图
  - `anomaly_name/anomaly_level`：异常类型与等级

- **摄像头与流**：`camera`、`camera_stream`
  - `camera_stream.stream_name`：用于从 `stream_id` 推断 `camera_1/camera_2...`

- **媒体索引**：`media_asset`
  - `duration_ms`：用于异常回放时长计算


## 6. API 与返回结构（对前端/系统集成友好）

### 6.1 `POST /chat`

#### 请求（JSON）

```json
{
  "session_id": "browser-001",
  "prompt": "今天张三做了什么？",
  "image": "<base64>"
}
```

#### 请求（multipart/form-data）

- `prompt`: 文本
- `file`: 图片文件（可选）
- `session_id`: 会话标识（可选，也可通过 `X-Session-ID` 请求头传入）

响应始终包含实际使用的 `session_id`。后续请求继续传入该值，普通问答即可使用历史上下文。

#### 清空记忆

```bash
curl -X DELETE \
  http://127.0.0.1:8002/sessions/browser-001/memory
```

#### 响应：三类典型 `type`

- `type=normal`：普通问答
- `type=reid`：熟人轨迹/报告汇总
- `type=vad`：异常汇总

（1）**ReID 响应（示意）**

- `tracklet`: 统计信息（total、camera_1..camera_4）
- `data.trackletN.image`: base64 图片
- `data.trackletN.recording`: 回放 URL
- `summary`: 大模型对多段报告的简要总结

（2）**VAD 响应（示意）**

- `date`: 标准化日期（YYYY-MM-DD）
- `tracklet`: 各摄像头异常数统计
- `data.trackletN.image`: 异常帧 base64
- `data.trackletN.recording`: 回放 URL
- `summary`: 大模型对异常报告的聚合总结


## 7. 与流媒体回放后端的交互（URL 约定）

`ReidService` 内部构造回放 URL（默认 `http://192.168.108.238:9996`，可通过 `--playback-base-url` 配置）：

- 轨迹回放：
  - `path=live/<camera_X>`
  - `start=<tracklet.start_ts>`
  - `duration=<end_ts-start_ts>`

- 异常回放：
  - `start=<vad.created_at>`
  - `duration` 优先取 `media_asset.duration_ms`，否则默认 30 秒

该 URL 由前端直接用于播放，无需本服务代理视频数据。


## 8. 部署与配置

### 8.1 启动示例

推荐使用启动脚本。脚本会静默等待共享 SGLang 可用，然后启动 Agent：

```bash
DB_HOST=<PG_HOST> \
DB_USER=<PG_USER> \
DB_PASSWORD=<PG_PASSWORD> \
DB_NAME=<PG_DB> \
PLAYBACK_BASE_URL=http://<PLAYBACK_HOST>:9996 \
MEMORY_MAX_SESSIONS=1000 \
MEMORY_MAX_MESSAGES=20 \
./scripts/start_agent.sh
```

也可以直接启动：

```bash
python llm_agent_service/main.py \
  --host 0.0.0.0 --port 8002 \
  --llm-backend sglang \
  --db-host <PG_HOST> --db-user <PG_USER> \
  --db-password <PG_PASSWORD> --db-name <PG_DB>
```

启动后检查：

```bash
curl http://127.0.0.1:8002/health
curl http://127.0.0.1:8002/ready
```

### 8.2 PostgreSQL 驱动

`create_pg_engine` 会按顺序尝试：`pg8000` / `psycopg` / `psycopg2`。如缺失会报错提示安装。


## 9. 计划书可用的亮点表述（建议写法）

- **以 PostgreSQL 为“数据中台”**：统一承载轨迹、异常、事件、报告、媒体索引与向量特征（pgvector），实现多服务解耦。
- **大模型与传统算法融合**：算法提供可解释的结构化证据（轨迹点、关键帧、异常标签），大模型负责语义理解与跨记录总结。
- **面向大屏的结构化输出**：返回 JSON 同时包含“可读摘要 + 可视证据（图/回放链接）+ 统计信息”，降低前端集成成本。
- **可扩展架构**：通过增加新的关键词/规则或新数据表，即可扩展更多查询能力（陌生人库、跨摄像头关联、重点区域事件等）。


## 10. 已知边界与后续扩展点

- **鉴权**：当前接口未做鉴权/权限控制，适合内网部署；计划书可写为后续增强（JWT、网关、签名）。
- **规则路由可升级为 Agent**：目前通过关键词与熟人命中实现确定性路由，后续可引入可控的工具调用 Agent（但需配套可观测与安全限制）。
- **更强的数据库约束与索引**：pgvector 索引、轨迹时间索引、外键与一致性校验可进一步完善。
