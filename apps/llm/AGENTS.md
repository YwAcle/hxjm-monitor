# 工作范围与 Git 协作规则

## Git 操作保持简洁

- 每次修改以完成内容为主，只执行必要的建分支、提交、合并和收尾操作，不把小改动变成复杂的 Git 流程。
- 开始时一次性确认当前分支和已有改动；修改过程中不反复检查状态、上游、历史、分支关系或 worktree。同一任务已知的信息直接复用，只有操作失败或出现新的冲突迹象时才补充检查。
- 可能的远端冲突集中在提交收尾阶段关注和处理，不在每次编辑前后检查远端。需要同步或已授权推送时，在该阶段获取一次远端更新并按下方规则处理；纯本地修改不为提交额外联网。
- 连续的必要操作尽量合并执行，失败即停；完成后只确认一次最终状态，不额外安排重复检查。

## 唯一维护的仓库

- 所有项目读取、搜索、扫描、修改和 Git 操作必须限定在当前项目的 Git 仓库内。执行命令时，将工作目录显式设为当前设备上的仓库根目录，或使用 `git -C` 指定该目录。
- 不要在仓库的父目录执行目录枚举、递归搜索、文件扫描或 Git 操作，也不要读取或修改同级的其他文件和目录。
- 如需操作仓库以外的文件，必须由用户明确指定范围。
- 不要在仓库的父目录初始化 Git 仓库，也不要把仓库外的同级文件纳入当前仓库。

## 拉取与推送

- 开始仓库任务时，一次性查看当前分支和工作区状态；上游配置仅在提交收尾确需远端同步时读取。本地修改默认基于当前检出的版本进行，不把 `fetch` 或 `pull` 作为每次修改、提交或本地合并的前置步骤。
- 仅在用户明确要求同步远程、当前任务确实依赖远程更新，或准备执行已获授权的推送时同步远程。同一任务中的连续修改不重复拉取。
- 同步时先获取对应远程的更新并检查分支关系；仅在本地落后且可以快进时执行 `git pull --ff-only <remote> <branch>`，明确指定实际远程和分支。已同步或仅本地领先时无需拉取；分支分叉时按下方冲突规则处理。
- 对已包含远程同步的修改任务，在提交收尾阶段先同步目标分支，再合并任务分支；只有修改本身依赖远端更新时才提前同步。避免先在过期的本地主线上生成任务合并提交，随后又补一次远程合并。纯本地任务仍不强制联网。
- 如果有未提交改动可能受到拉取影响，先告知用户并等待处理决定；不要自行 stash、丢弃、覆盖或提交这些改动来完成拉取。
- 没有上游不阻止本地工作；确需同步但无法确定远程和分支时，再向用户确认。对于未产生冲突或分叉的临时同步错误，可以进行只读诊断和安全重试；仍失败时报告原因，暂停依赖该同步的操作，不阻止独立的本地修改和本地合并。
- 用户要求的仓库改动按下述流程提交并在本地合并。推送须在用户授权范围内；推送前按上述规则处理远程更新，同一收尾阶段已获取的结果直接复用，不重复获取。若推送因远端再次更新而被拒绝，再获取并处理，不强制推送。
- 跨设备或多人协作时，尽量串行集成到同一目标分支；已授权推送的任务合并后及时推送，下一个集成者先同步。双方已各自推进主线时，按分叉规则处理，不能为整理图形撤销或重做已有合并。

## 先建分支，再修改，最后合并

- 以一个可独立交付的修改目标作为任务单位。任务内同一图表、段落或规则的连续调整使用同一分支，可有多个提交，完成后只合并一次；不要按每个文件、每次措辞或格式调整拆分支。任务已经合并后，后续新请求从目标分支新建分支，不继续使用旧分支。
- 每项独立修改任务开始前，记录当前分支作为目标分支，创建并切换到新的任务分支（例如 `git switch -c codex/<简短任务名>`），之后才开始修改。新任务分支统一使用 `codex/` 前缀；已有分支不为统一命名而改名。当前已在本任务的未合并分支时继续使用它，并沿用记录的目标分支；避免在任务分支上再套任务分支。不要直接在目标分支上改动。
- 新建的本地任务分支没有上游是正常情况，无须为此创建远程分支。确需远程同步时，以目标分支对应的远程和分支为准。
- 用户仅要求 commit、pull、push 时，先检查是否有待提交内容；有内容才按任务分支流程提交，无内容则只同步已有提交，不创建空任务分支或空提交。
- 完成改动后按本文件的构建约定执行必要检查，仅提交本次任务涉及的改动，不要纳入用户已有或无关的改动；未经用户明确要求，不自动编译或检查 PDF。
- 完成提交后，切回目标分支，按上述规则完成当前任务需要的远程同步，再使用 `git merge --no-ff <任务分支> -m "Merge <任务分支>: <修改目的>"` 合并。每项任务保留一个明确的合并入口，即使可以快进也创建合并提交，保留分支拓扑；不为展示分支形状额外创建空合并。
- 任务分支合并不使用快进合并或 squash；不要自行 rebase 或改写历史。通常直接在目标分支合并任务分支，不先将目标分支反复合入任务分支；确有依赖需要时再处理。
- 上述 `--no-ff` 规则适用于任务分支合并，不改变远程同步时的 `--ff-only` 及分叉处理规则；不能用 merge 绕过需要用户决定的远程分叉。
- 合并遇到冲突立即停止，告知用户并等待决定，不自动解决或中止合并。
- 合并完成后确认 Git 状态；如已授权推送，再按上述远程同步规则推送目标分支。

## 分支收尾与历史查看

- 本次创建的临时任务分支成功合并后，直接用 `git branch -d <任务分支>` 删除本地分支引用，由 Git 自身检查未合并提交和 worktree 占用，不另行反复查询。删除被拒绝时保留并说明原因，不使用 `-D`。合并提交仍保留分支形状和任务名称，无需长期保留已完成分支的标签。
- 批量清理历史遗留分支或删除远程分支须由用户单独授权；不要顺带删除旧分支、未合并分支或其他人的工作分支。
- 查看集成顺序时优先使用 `git log --first-parent --oneline <目标分支>`；查看任务分叉时使用 `git log --graph --oneline <目标分支>`。仅在排查所有分支时使用 `--all`，避免将无关分支和标签混入日常视图。
- 已发布的快进历史、远程同步合并和旧分支拓扑保留原样；不为美化提交图重写历史、补造历史合并或强制推送。

## 冲突由用户决定

- 任何 Git 操作遇到冲突时，立即停止后续修改、提交和推送。
- 告知用户触发冲突的操作、涉及的文件和当前 Git 状态，通过只读查看说明双方的实质差异；明确区分冲突块和已自动合并的改动。
- 主动提供带编号的具体选项，例如保留本地版本、采用对方版本、组合双方内容（可行时）。每项简要说明保留哪些内容及其影响，明确选择作用于冲突块还是整个文件；有依据时将推荐方案置于首位并说明理由，不只笼统询问“如何处理”。多处冲突按文件或冲突块分组，让用户可直接回复选项编号。
- 未得到用户明确指示前，不要自动解决冲突、选择 ours/theirs、继续或中止 merge/rebase，也不要 reset、强制推送或以其他方式覆盖内容。
- 检查发现本地和上游各有独有提交时，即使尚未执行 `pull` 或产生文件冲突，也按同样原则停下，说明分叉情况并主动给出带编号的整合选项及其影响，请用户决定；对当前分叉已获得的授权无需重复询问。
