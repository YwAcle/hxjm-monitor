# 场景描述
	 ZLM hook -> 帧解码->格式转换 RGB->放入 inQueue队列->AiTaskQueue从队列取->AiTaskQueue 多线程做 zeroMq + shmmsg 与 python 通信做算法处理 -> python 处理结果写入 shmmsg ->AiTaskQueue 读取结果，放入outQueue-> 格式转换 YUV -> 帧编码-> ZLM 推流 

上述是 custom_module 模块，对 zlm 服务器插入 AI 处理的整个逻辑。

	存在问题：播放流时，开始延迟 1s，随着时间增长，延迟增长到 30s+，还会继续增长
# 解决
## AI 处理模块太慢
- 理论分析，AI 处理耗时 300ms，AI 10 个线程并发处理，那么一帧相当于 30ms 处理，一秒能处理 1000/30=33 帧 > 25帧
- 如果是因为编解码的时间，导致耗时增大，从而导致一秒 < 25帧，那么可能影响
- 解决：
	- AI 处理耗时取消 sleep
	- 打印编解码时间
- 结论：
	- **不是这里问题**，AI 处理耗时几毫秒级，打印也是几毫秒级，仍然有延迟
## 队列缓冲太多，时间堆叠
- inQueue 和 ThreadPool 里无限队列长度，以及 outQueue三个队列，可能有堆叠导致延迟
- 解决：
	- 打印三个队列的item 长度
- 结论：
	- **不是这里问题**，三个队列内元素的长度，基本都是 0 / 1 ，不存在堆叠
## 时间戳问题
- decoder 两帧时间差 != encoder 两帧时间差，会导致时间戳偏移
- 解决：
	- 打印两帧的时间
	- dec gap = 120ms 左右，即 8 帧/sec
	- enc gap = 40ms 左右，即 25 帧/sec
	- 很奇怪，如果是堆叠，我是先 dec 再 enc，那么应该是 dec gap < enc gap，从而导致堆叠。
- 问题：
	- initEncoder 时，没有设置_encCtx 的 timebase，即设置 `_encCtx->timebase = {1,90000}`，zlm 本来输入的是{1,1000}，需要转成 h264 的标准 90kHz
	- decoderFrame 函数中，对于 时间戳，av_parser_parse2有就用_parse->pts，没有用 frame->pts，这里是有问题的，h264 应该默认是 90kHz，而不是 frame 的，要做转换
	- encoderFrame 时，要把 pts 从{1,90000}，转成{1,1000} 
- 结论 ：
	- 开始dec gap = 40ms 左右，随着时间增加，还是会增大，而且波动范围很大，大部分85-120
	- enc gap 大部分 40ms 固定， 十几个40ms，出现 1 次 80ms 和 1 次-40ms
## poller 线程阻塞，导致喂给decoder数据波动
- decoder 两帧间隔长，即输入 decoder 的帧率只有 8 帧/sec
- dec 操作的解码与像素转换放在事件线程里执行，如果 poller 阻塞，那么就会输入 decoder 很慢
- 长期运行时，会出现 async_l timeout，提示 poll 处理超时，这个可以侧面验证
- 解决：
	- hook 的帧，放入一个队列缓存
	- 起新 thread 来做 decoder，把解码、ai 处理、编码都用子线程来做，不依赖于 io 转发的 poller
- 问题：
	- enc gap 仍然是 40，偶尔-40 和 80（次数可忽略）
	- dec gap 会一段时间 40 左右，然后突然增大一会，大概 100ms，然后又恢复 40 左右
- 结论：
	- AI 处理 200 ms 时，延迟还是会增大，只是时间变缓慢了
	- AI 处理 sleep = 0 时，延迟好像不会增大
	- 可能是并发数不够，Ai 处理这延迟
## 新问题：画面抖动
- 解决了延迟，但是画面抖动问题很严重
- av_parser_parse2 得到的 pts 的 dts 不可靠，因此会导致抖动
- av_parser_parse2 得到的 nalu 分片，只用来 decoder 解码读 nalu，不用 pts
- 解决：
	- decoder 的 pts 用源的，通过 av_rescale_q 做时间基转换
	- encoder 的 pts 自己维护，每次编码后加 timebase(1/90000) / fps(25) = 3600

# 总结
1. 时间戳问题，传入的时间基是 1kHz，但是 h264 的标准是 90kHz，因此编解码时，都要对时间基做一次转换，否则会导致帧间间隔不对，导致播放延迟（主要原因）
2. 时间基问题，encoder 用的 decoder 的时间基，会受 ai 处理的影响，导致 pts 不稳定，从而产生画面抖动，通过自己维护 pts 来解决
3. 解码+sws_calse用 poller 的线程，但是 poller 线程被 io 这些复用，导致线程任务过重，阻塞，导致解码/转换慢，提示 warn async_l timeout ，用队列+子线程单独处理即可（次要原因）
