# hxjm-algdeployment（算法部署/大屏数据服务）功能说明

## 1. 模块定位
`hxjm-algdeployment` 是智慧监控系统中面向“大屏展示 + 算法任务启动”的后端服务模块，核心职责是：

- **以 PostgreSQL 为中心做数据汇聚与查询**：告警事件、行人轨迹、人脸识别事件、LLM 分析报告、媒体片段索引等均以表形式沉淀在数据库中。
- **对接算法服务端**：支持按任务启动算法容器/脚本，并生成统一的直播流访问 URL；同时接收算法/流媒体侧回调写入媒体片段索引。
- **对接前端大屏**：提供 REST API（初始化统计/列表/详情）与 WebSocket（实时推送告警、人流、LLM 报告）。
- **对接流媒体后端（MediaMTX 等）**：拼接回放/截取 URL、约定直播流 path 命名规则，供前端直接播放。

> 说明：你提到“PostgreSQL 可以存 torch（模型权重）”。在本模块源码中未发现直接存取 `.pt/.pth`、`bytea/large object` 的实现；更像是系统整体依赖 PostgreSQL 存储图像 base64、事件元数据、报告 JSON 等。本说明会在“可扩展点”中给出“模型/torch 存储”的落地建议，便于写计划书。

---

## 2. 技术形态与工程结构
- **技术栈**：Spring Boot（Web + WebSocket + Scheduling）、MyBatis Mapper（XML SQL）、Fastjson2。
- **目录结构（关键包）**：
  - `controller/`：REST API
  - `service/`、`service/impl/`：业务逻辑
  - `mapper/` + `resources/mapper/algdeployment/*.xml`：数据库访问与 SQL
  - `websocket/`：大屏实时推送（轮询 DB + WebSocket 推送）

---

## 3. 以 PostgreSQL 为中心的数据中枢：数据对象与表
本模块通过 MyBatis SQL 显式引用/关联的主要表如下（按功能域划分）：

### 3.1 设备与流关联
- **`camera`**：摄像头表（用于统计设备数量）
- **`camera_stream`**：摄像头与流名的映射（`stream_name`、`camera_id` 等），用于把算法侧的 `stream_id` 反查为前端展示的 `camera_code`

### 3.2 告警/异常检测（VAD 等）
- **`vad`**：异常检测事件（本模块重点使用 `anomaly_name in ('fight','fire','fall')`、`created_at`、`frame_vad_base64`、`stream_id`、`media_asset_id`）

### 3.3 轨迹/人流与身份（ReID/陌生人/人员库）
- **`tracklet`**：目标轨迹，用于人流统计、陌生人数量、最新识别记录等（使用字段包括 `start_ts`、`stream_id`、`gallery_target_id`、`stranger_target_id`）
- **`reid_target`**：人员库目标（用于在大屏上展示已识别人员的 `name`、`image_base64`）
- **`reid_match`**：ReID 匹配事件累计数（用于大屏 AI 计数）

### 3.4 LLM 报告与会话计数
- **`llm_report`**：LLM 生成的结构化/文本报告（使用 `id(uuid)`、`created_at`、`prompt_type`、`report_json`、`report_text`、`episode_id`、`vad_id`）
- **`episode`**、**`episode_tracklet_link`**：报告与事件片段/轨迹的关联（用于 ReID 类型报告的播放、缩略图等）
- **`chat_count`**：大屏“对话/问答”累计计数（用于 AI 总计）

### 3.5 媒体片段索引（回放/证据链）
- **`media_asset`**：媒体资产索引表（本模块写入并查询），关键字段：
  - `id uuid`
  - `stream_id`：流标识（通常与 MediaMTX path 对应）
  - `start_ts`、`duration_ms`
  - `path`：片段在文件系统/对象存储/流媒体服务的可访问路径
  - `content_type`、`meta`、`created_at`

### 3.6 算法部署管理（管理端）
- **`alg_bk_management`**：算法后端服务注册表（算法名称、类型、API 前缀、启用状态、对应设备状态表等）
- **`ba_machine`**、**`alg_bk_machine_fr`**：设备表与“算法部署状态”关联（用于列表展示设备可用性与部署状态）

### 3.7 人脸识别事件（管理端/大屏）
- **`face_recognition_events`**：传统人脸识别事件表（含 `detection_img` 等）
- **`face_recognition_events_v1`**：大屏统一事件表（引入 `identity_type`，可统一关联人员/陌生人）
- **`face_person`**：正式人员库
- **`face_stranger`**：陌生人库
- （遗留关联）**`face_database`**：在旧 SQL 中用于 `face_id -> user_name` 映射

## 4. 与外部系统的交互链路（端到端数据流）

## 4.1 算法任务启动 → 生成直播流 URL
对应代码：`AiTaskRunController` + `AiTaskRunServiceImpl`

- **入口**：`POST /algdeployment/ai/tasks/{task}/runs`
- **输入**：JSON body 必填 `camera_id`（数字）
- **动作**：
  - 优先尝试执行 `docker compose -f <composeFile> up <service> -d` 拉起算法容器
  - 若 compose 不可用或失败，则在本机启动 Python 进程（可选 conda 环境）并做简易“守护重启”
- **输出**：返回统一直播流 URL：
  - `http(s)://{host}:{livePort}/live/camera_{cameraId}_{task}`

### 直播流命名约定
- `live/camera_{cameraId}_{task}` 是本系统中非常关键的跨系统约定：
  - **算法服务端**推流/写流通常使用该 path
  - **流媒体后端（如 MediaMTX）**对外提供播放
  - **前端大屏**直接使用该 URL 播放/预览

### 关键配置（来自 `hxjm-common` 的 `AiTaskProperties`）
本模块直接使用的关键配置项包括（名称以代码含义为准）：
- `composeFile`：docker compose 文件路径
- `tasks.<task>`：任务配置（`composeService`、`pythonDir`、`entry` 等）
- `mtxHome`：算法/流媒体工作目录基路径（用于定位 `pythonDir`）
- `condaInit`、`condaEnv`：可选 conda 启动参数
- `publicHost`：对外域名/IP（用于生成前端可访问 URL）
- `livePort`：直播端口
- `mtxBaseUrl`：回放/截取服务 base（用于拼接 `/get?path=...&start=...&duration=...`）

---

## 4.2 算法/流媒体 → 媒体片段索引入库 → 大屏/回放
对应代码：`MediaAssetController` + `MediaAssetServiceImpl` + `MediaAssetMapper.xml`

### 4.2.1 写入媒体资产（供算法/流媒体回调）
- **接口**：`POST /media-assets`（匿名）
- **请求字段**：
  - `stream_id`：流标识
  - `segment_path`：片段路径
  - `duration_s`：片段时长（秒）
- **行为**：
  - 解析 `segment_path` 中的时间戳，落库为 `start_ts`
  - 转换 `duration_s -> duration_ms`
  - 插入 `media_asset` 表

### 4.2.2 查询媒体资产
- **接口**：`GET /media-assets`（匿名）
- **返回**：最近 200 条媒体资产（按 `created_at desc`）并额外拼接 `play_url`

### 4.2.3 回放/截取 URL 生成（与 MediaMTX 交互）
- `MediaAssetServiceImpl#buildPlayUrl` / `ScreenServiceImpl#buildMtxPlayUrl` 生成类似：
  - `http://{host}:9996/get?duration={seconds}&path={streamId}&start={timestamp}`

这体现了系统的“**数据库存索引，播放由流媒体服务承载**”的设计：
- DB 负责持久化：发生了什么、何时发生、对应哪个流、对应哪个片段
- 流媒体服务负责：按参数裁剪/回放，前端直接播放

---

## 4.3 大屏 REST：初始化统计与基础指标
对应代码：`ScreenController` + `ScreenServiceImpl` + `ScreenMapper.xml`

### 4.3.1 设备数量
- **接口**：`GET /api/device/stats`（匿名）
- **数据来源**：`select count(1) from camera`

### 4.3.2 大屏初始化数据（通过 WebSocket init 下发）
虽然没有 REST 暴露完整 init，但在 WebSocket 连接建立时会调用：
- `screenService.getAlarmInitData()`：告警大屏 init
- `screenService.getPedestrianInitData()`：人流大屏 init

这些 init 本质上都是从 PostgreSQL 聚合得到：
- 今日异常总数、分类型计数（fight/fire/fall/stranger）
- AI 总计（vad + stranger + reid_match + llm_report + chat_count）
- 最近告警列表（最近 5 条）
- 今日人流总计（tracklet）
- 最近识别到的人员列表（reid_target + tracklet）
- 10 分钟粒度的流量曲线（tracklet 聚合）

## 4.4 大屏 WebSocket：实时推送协议
对应代码：`AlarmWebSocketConfig` + `AlarmWebSocketHandler` + `LlmReportWebSocketHandler`

### 4.4.1 WebSocket 端点
- **`/ws/alarm`**：告警大屏（fight/fire/fall/stranger 等）
- **`/ws/pedestrian`**：人流大屏（今日累计、10分钟增量、最新身份）
- **`/ws/llm-report`**：LLM 报告大屏（init + 增量 append）

### 4.4.2 通用心跳
- 客户端发送：`{"type":"ping"}`
- 服务端返回：`{"type":"pong"}`

### 4.4.3 `/ws/alarm` 推送类型
- **init**：`{"type":"init","data":{...}}`
- **new_alarm**：当检测到最新告警或陌生人变化时推送
  - `data.ai_count`：AI 总计
  - `data.anomaly_update`：本次变化（type + count + total）
  - `data.alarm`：最新告警信息（id、alarm_level、event_type_key、camera_id、thumbnail、record_url、timestamp）

实现方式：
- `@Scheduled(fixedDelay=...)` 每 2s 轮询 DB
- 通过 `lastAlarmKey/lastStrangerKey` 去重，仅有新数据才推送

### 4.4.4 `/ws/pedestrian` 推送类型
- **init**：`{"type":"init","data":{...}}`
- **metrics**：当 tracklet 有新数据时推送
  - `total_today`：今日总人流
  - `ai_count`：AI 总计（vad + flow + reid + llm + chat）
- **new_identity**：当检测到最新身份记录变化时推送
  - `identity`：统一结构（name/avatar/camera_id/detected_time/identity 等）
- **flow_update**：每 10 分钟推送一次增量（`selectFlowCountBetween`）

### 4.4.5 `/ws/llm-report` 推送类型
- **init**：`{"type":"llm_report","op":"init","data":{"items":[],"cursor":...}}`
- **append**：`{"type":"llm_report","op":"append", ...}`

特点：
- 维护游标：`lastCreatedAt + lastId(uuid)`，避免重复推送
- 对不同 `prompt_type` 做不同拼装：
  - `reid`：优先取轨迹帧 `reid_frame_end_base64`，否则从 `episode_meta` 解析人像；并用 `ScreenServiceImpl#buildMtxPlayUrl` 拼接 `record_url`
  - 其他（如 `vad`）：取 `frame_vad_base64` + 根据 row 拼 `record_url`

## 5. 人脸识别业务（大屏列表/弹窗）
对应代码：`FaceRecognitionEventController` + `FaceRecognitionEventServiceImpl` + `FaceRecognitionEventMapper.xml`

### 5.1 管理端 CRUD（传统表）
- `GET /algdeployment/face_recognition_events/list`
- `GET /algdeployment/face_recognition_events/{id}`
- `POST /algdeployment/face_recognition_events`
- `PUT /algdeployment/face_recognition_events`
- `DELETE /algdeployment/face_recognition_events/{ids}`

### 5.2 大屏接口（v1 统一表）
- **今日事件列表（大屏）**：`GET /algdeployment/face_recognition_events/getTodayEvents`（匿名）
  - 返回 `TodayFaceEventVO`，统一 PERSON/STRANGER 的 `displayName`
- **事件 + 身份详情（弹窗）**：`GET /algdeployment/face_recognition_events/{id}/identityDetail`
  - 返回 `FaceEventIdentityDetailVO`（事件信息 + 身份信息统一结构）

### 5.3 陌生人转正式人员（历史事件回填）
- Mapper 提供：`updateEventsIdentityFromStrangerToPerson(strangerId, personId)`
- 语义：把 `face_recognition_events_v1` 中某个陌生人的历史记录批量改为正式人员

> 备注：`FaceRecognitionEventMapper.xml` 中存在 `CURDATE()/IFNULL()` 等更偏 MySQL 的写法，而本模块其它 SQL 大量使用 PostgreSQL 风格（`date_trunc`、`interval`、`::uuid` 等）。若你在计划书中描述，可归纳为“历史兼容/逐步迁移阶段”。

## 6. 算法部署管理（设备侧部署状态与配置）
对应代码：`AlgDeploymentManagementController` + `AlgDeploymentManagementServiceImpl` + `AlgDeploymentManagementMapper.xml`

- 典型管理端 CRUD：
  - `GET /algdeployment/management/list`
  - `GET /algdeployment/management/{id}`
  - `POST /algdeployment/management`
  - `PUT /algdeployment/management`
  - `DELETE /algdeployment/management/{ids}`
- 设备可用列表：
  - `GET /algdeployment/management/getMachineList`
  - SQL：从 `ba_machine` 取设备并 LEFT JOIN `alg_bk_machine_fr` 获取 `deployStatus`

该模块在系统架构中承担“**算法与设备/摄像头绑定的配置面**”，便于运维侧管理算法启停、部署状态展示。

## 7. 安全与访问控制特征
- 多数管理端接口使用 `@PreAuthorize` 做权限控制
- 大屏与算法回调接口多标注 `@Anonymous`，便于无 token 的设备/大屏访问

在计划书中可强调：
- 管理端（运维/管理员）与展示端（大屏）做了权限分层
- 对外 WebSocket 允许跨域（`setAllowedOrigins("*")`），适合大屏场景快速集成

## 8. 可扩展点（计划书可写亮点）

### 8.1 “PostgreSQL 存 torch/模型”如何落地
当前模块未直接实现模型持久化，但可作为系统整体能力扩展：
- **方案 A：`bytea` 存储**
  - 表：`model_artifact(id uuid, name, version, sha256, content bytea, meta jsonb, created_at)`
  - 适合中小模型/特征向量/torch tensor 序列化（例如 `torch.save` 后的二进制）
- **方案 B：Large Object（OID）存储**
  - 表仅存 OID + 元数据；真实内容走 PG large object
  - 适合较大文件，便于流式读写
- **方案 C：对象存储（MinIO/S3）+ PostgreSQL 存索引**（与 `media_asset` 的思路一致）
  - 数据库存：路径、版本、hash、任务绑定关系
  - 文件存：对象存储

你可以在计划书中强调：
- “统一资产中心（PostgreSQL 索引/元数据）”
- “大对象可扩展（模型权重、特征库、证据视频）”

### 8.2 大屏实时性与性能
目前方式是“轮询 DB + WebSocket 推送”。可进一步升级：
- 使用 `LISTEN/NOTIFY`（PostgreSQL）或消息队列（Kafka/RabbitMQ）做事件驱动
- 在热点统计上引入 Redis/TimescaleDB 分区等

## 10. 总结
`hxjm-algdeployment` 是“智慧监控大屏展示与算法任务调度”的关键模块：
- **数据库中心**：将算法侧的事件、轨迹、报告、媒体索引统一沉淀在 PostgreSQL
- **多端协同**：REST + WebSocket 同时支撑管理端与大屏实时展示
- **流媒体联动**：通过统一的 `stream_id/path` 规则与 `/get` 回放接口实现“证据链播放”

该模块非常适合在挑战杯计划书中作为“**数据中台 + 实时可视化 + 智能算法调度**”的落地证明。
