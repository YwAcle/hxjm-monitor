# 图片引用与多轮视觉记忆实施计划

编写日期：2026年10月4日。

状态：第二阶段设计草案，供评审。本文件中的图片资产表、上传接口、image_id、图片状态和生命周期作业均未实现，不能按现有接口使用。

## 1. 目标与现状

第一阶段已为 `/chat/stream` 增加 JSON 和 multipart 文件上传支持；两种输入规范化后进入现有 Agent 真实流式正文生成链路。普通 `/chat` 保留兼容性。监控聊天前端不在当前仓库中，调用方仍需把图片分析请求切换到流式接口。

当前记忆只保留用户文字和助手正文，不保存原图。用户上传图片后追问“左上角是什么”，如果不再次传图，模型只能参考之前的文字描述。这不足以支持可靠的视觉细节判断。

第二阶段的目标：

- 图片上传一次，后续在所属会话中通过引用重新提供原图给模型。
- 图片与文字问答共用 `/chat/stream`，最终正文只生成一次。
- 图片来源、归属、当前任务和有效期可追溯，支持明确删除。
- 不把 Base64 长期塞进聊天消息、摘要或日志。
- 区分看图描述与查询监控身份；不得仅凭图片引用声称数据库已确认人员身份。

不在本阶段实现：跨用户图片共享、图库相似度搜索、人脸长期档案、向量图片记忆、视频帧库、跨图自动关联人物。

## 2. 方案选择

建议先使用 PostgreSQL 保存图片元数据，受控文件存储保存图片原始字节。部署为单实例时可以使用持久化磁盘目录；多实例必须使用共享文件存储或对象存储，不能把某个实例的本地路径当作共享图片引用。

`image_id` 是服务生成的不可预测标识，数据库记录不暴露内部路径。模型调用前由后端读取图片并临时转换成 Data URL。初期不把存储 URL 直接交给模型，也不接受任意远程 URL，避免访问权限泄漏和服务端请求伪造风险。

图片引用不是权限凭据。`session_id` 目前只是会话定位符，也不能代替可信用户身份。

## 3. 建议数据结构

以下字段名为规划命名，可以在实现评审时调整。

### 3.1 图片资产表 `agent_image_assets`

| 字段 | 用途 |
| --- | --- |
| `image_id` | 图片逻辑标识，主键。 |
| `tenant_id`、`owner_id` | 可信身份上下文中的租户和所有者，禁止客户端自行指定。 |
| `session_id` | 绑定的会话，仅用于归属关联，不用于鉴权。 |
| `storage_key` | 内部存储键，不向客户端和模型暴露。 |
| `media_type`、`byte_size`、`width`、`height` | 经验证的图片属性。 |
| `content_hash` | 完整性验证与同作用域幂等处理，不用于跨用户复用权限。 |
| `status` | `uploading`、`ready`、`deleting`、`deleted`、`failed`。 |
| `created_at`、`expires_at`、`deleted_at` | 有效期和删除状态。 |

文件名只能作为可选展示信息，不能直接组成磁盘路径。模型读取时检查状态、归属、有效期和完整性。

### 3.2 会话图片状态

| 字段 | 用途 |
| --- | --- |
| `active_image_id` | 当前任务的图片引用。 |
| `active_task_id` | 区分看图、超分等任务，防止旧意图误用。 |
| `state_version`、`generation` | 并发提交和清空竞态保护。 |
| `updated_at` | 最近一次明确选择图片的时间。 |

用户消息另记录 `attachment_image_ids`，保留“该轮实际上看了哪张图”的关联。仅保存助手描述不能代替这份关联。状态和关联的持久化需要与会话 Repository 方案一起实施，不能只新增图片表却继续依赖无持久化的 active_image_id。

## 4. 建议接口契约

### 4.1 上传图片

规划接口：`POST /images`，使用 multipart 的 `file` 和 `session_id`。

返回示意：

```json
{
  "image_id": "服务生成的图片标识",
  "session_id": "所属会话",
  "media_type": "image/png",
  "width": 1600,
  "height": 1600,
  "expires_at": "服务生成的有效期时间"
}
```

若上传时尚无会话，服务先创建会话并返回其标识；前端必须在后续对话中使用同一会话。可信用户归属来自服务端身份，不接受表单中的 owner_id。

### 4.2 发起视觉对话

规划 JSON 请求：

```json
{
  "prompt": "这张图左上角是什么？",
  "session_id": "所属会话",
  "image_ids": ["已上传图片标识"]
}
```

初版限制为一张图片。`image_ids` 与 `file`、Base64 互斥，混用返回明确的 400 错误，不自行猜测优先级。

第一阶段的直传图片接口继续兼容。第二阶段直传图片需要先生成图片资产，再执行对话；通过 SSE 的独立 `attachments` 事件返回已绑定的图片引用，前端兼容后启用。上传成功但生成失败时，引用仍可用于重试，不能只能在成功的 `done` 事件中返回图片 ID。

现有 `delta` 正文格式保持不变。新增 `attachments` 事件不得携带 Base64、内部路径或未经授权的下载链接。

### 4.3 图片删除

规划接口：`DELETE /images/{image_id}`。校验归属后先标记不可用，再清除会话 active_image_id，最后异步删除文件并完成状态转换。重复删除应幂等。

未知或无权访问的引用统一返回不暴露资产存在性的错误。已授权会话内的过期、已删除图片可返回重新上传的提示。

## 5. 图片选择与多轮指代

选择顺序：

1. 当前请求明确上传或指定的图片。
2. 明确的视觉追问，且当前任务只有一个有效 active_image_id。
3. 没有有效图片或存在多个候选时，澄清或要求重新上传。

不能为每一轮消息自动附加上一张图。“昨天的异常有几条”应查询数据库，不必把上一张动漫图带给模型。模型可以提出“该问题需要当前图片”的意图，但图片归属和选择必须由服务校验。

第一版仅支持“当前这一张图”。“上一张”和“这两张比较”留给后续明确的图片序列与多图输入设计，不能通过猜测摘要实现。

新上传图片成为当前图片，但不得自动继承上一张图的超分意图。超分任务绑定 task_id 和 image_id，执行完毕后清除待完成状态，保留资产引用供明确追问。

每个请求在开始执行时快照图片引用和状态版本，不能在模型调用中途重新读取一个已被另一个请求换掉的 active_image_id。

## 6. 流式一致性与失败恢复

- 图片解析、权限校验、存储可用性检查在开始正文输出前完成。
- 最终视觉正文直接基于原图、用户问题和经验证工具证据生成，不先生成完整答案再复述。
- 完成时保存用户文字、实际图片引用和最终正文，并使用同一份正文记录 agent_end 与 request_end。
- 中断或截断保留已输出正文与失败状态，不保存成正常完成的问答。
- 图片上传成功与回答成功分开记录；失败回答不等于必须删除图片，前端可以用已有引用重试。
- 使用 request_id 防止重试重复写入；相同 ID 携带不同图片或问题时拒绝。
- 会话清空或图片删除后，在途请求不能重新提交旧图片引用。提交时检查代际、状态版本和图片有效性；已经发给模型或用户的内容无法追回，应记录在途请求的取消结果。

## 7. 安全与生命周期

建议初始有效期为可配置的24小时，不因被访问而无限延长；具体保留期需由业务和部署要求确认。

- 限制图片大小、格式、尺寸、单次数量、用户总容量和上传频率。
- 不记录图片 Base64、签名 URL、内部存储路径；日志仅记录引用、大小、尺寸、状态和错误码。
- 已有身份体系接入前，只能在可信单用户部署下试用；不得宣称 session_id 实现了多用户隔离。
- 临时上传与元数据提交采用 staged 状态和原子文件落位，清理孤儿文件及长期 uploading 记录。
- 清空会话同时使其图片引用失效，并清理对应会话上传资产；不删除共享的监控原始媒体。
- 若保留现有文本清空语义，应在接口中明确区分“清空对话”和“删除会话及附件”，不能静默变更保留行为。
- 删除采用可重试任务，覆盖存储文件、缓存、缩略图和未来的派生索引；数据库保留不含图片内容的删除审计。
- 服务重启后从持久化状态恢复；资产目录或对象存储不可用时明确报错，不让模型仅靠文字猜图。

## 8. 实施阶段

| 阶段 | 工作内容 | 交付物 |
| --- | --- | --- |
| A：契约与身份 | 确认用户归属、会话持久化、存储部署、TTL、清空语义和前端事件兼容 | 接口评审与迁移方案 |
| B：资产存储 | 新增元数据表、存储适配器、上传和删除接口、限额与孤儿清理 | 可独立测试的图片资产服务 |
| C：会话接入 | image_ids、active_image_id、消息附件关联、版本提交、attachments 事件 | 上传一次后的多轮视觉问答 |
| D：恢复与治理 | 重试幂等、过期、并发清空、删除竞态、重启和多实例测试 | 生命周期作业与验收报告 |

建议新增 `service/image_assets.py`、图片 Repository 和数据库迁移；在 `app.py` 接入引用解析，在执行器构建模型消息之前加载原图，在记忆模块维护引用状态。继续复用现有图片内容校验能力，不在各接口重复实现图像解析。

## 9. 验收案例

1. 上传一张图后不重传图片，追问“左上角是什么”；确认实际模型请求仍包含对应原图。
2. 上传新图后追问“这张图”；确认只使用新图，不继承旧超分任务。
3. 切换到数据库问题；确认没有自动附带无关图片。
4. 跨用户、跨会话、过期和删除引用全部被拒绝，不能凭知道 image_id 访问图片。
5. 清空会话与在途生成竞争；确认旧引用不能回写或复活。
6. 服务重启后可恢复有效引用；多实例轮流接收请求仍能加载同一图片。
7. 生成中断后图片可重试，未完成正文不成为正常历史；重复 request_id 不新增重复问答。
8. 正常视觉流式输出中，SSE 正文、日志和历史完全一致，且日志不含图片内容。
9. 清理作业可重试；资产过期或删除后，文件与可访问引用最终均被清除。

## 10. 评审时需确认

- 当前是否有可信用户/租户身份，还是仅单用户内部部署？
- 会话持久化是否与图片引用同步上线？
- 单实例持久磁盘是否足够，还是需要共享对象存储？
- 图片保留期、用户容量限额、删除审计与备份清理要求是什么？
- 第一版是否接受只支持当前单图，暂不支持历史序号和多图比较？
- 监控前端由哪个仓库维护，如何发布 image_ids 与 attachments 事件兼容？
